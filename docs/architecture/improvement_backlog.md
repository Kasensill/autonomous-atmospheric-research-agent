# Agent 工程改进 Backlog

> 来源：一次对检索、判断、重试、引用、工具、State、Memory 与报告安全性的外部建议审查。
> 原则：只记录经过项目现状验证后值得做的工作；不把通用经验数字当作必须照搬的规则。

## P0：报告安全路径

- [x] **零 evidence 且预算耗尽的受限报告**：与“核验失败后的受限报告”共用模板骨架，但展示不同
  失败原因和下一步建议；已补图级回归测试。

## P1：三 Agent 改造的必要前提

- [ ] **Evidence Review 反馈注入**：把 `missing_points`、冲突和定向补查要求作为结构化输入交回
  Research Agent，而非只让图泛泛回到 agent。
- [ ] **防震荡**：记录已执行的 `(tool_name, normalized_args)` 与已查 query；在反馈循环中避免重复查询。
- [ ] **上下文边界**：为 messages/evidence 定义当前节点需要的最小视图；避免网页正文和历史消息无限增长。
- [ ] **引用主张映射**：在保留现有 `[E#]` 存在性检查的基础上，记录关键主张对应哪些 evidence ID，
  让程序能够检查引用归属，而语义蕴含仍由模型审查。

## P2：评测驱动的检索提升

- [ ] **扩充领域词表**：根据漏检案例补 ENSO、ERA5、NCEP、CMIP6、WRF 等术语。
- [ ] **同义词/别名查询扩展**：从评测失败中收集词对，例如 ENSO 与“厄尔尼诺南方涛动”；先在查询侧
  扩展，不修改原始资料正文。
- [ ] **扩展评测集**：从当前 12 条高质量案例逐步扩展到约 50 条，保留预期来源标注。
- [ ] **Chunk 与 rerank 候选数实验**：用评测比较不同 chunk 粒度及 12、20、50 等候选数的质量、成本和
  延迟；不预设“300～600 字”或“20～50 候选”必然更好。

## P3：性能、工具与 Memory

- [ ] **工具调用缓存**：缓存安全的只读 `(tool, args)` 结果，并在 Trace 中明确标出 cache hit/miss。
- [ ] **超时策略补齐**：网页正文读取与节点级执行增加受控 timeout；保留当前天气和网页搜索的 HTTP timeout。
- [ ] **可并行的独立工具**：只在任务确实互不依赖时并行，避免破坏 Tool Calling 的因果顺序。
- [ ] **模型分层实验**：评测后再决定研究/写作与分类/审查是否使用不同模型，比较质量、成本和延迟。
- [ ] **Memory 升级**：从本地 JSON 摘要卡扩展到 SQLite/PostgreSQL、用户/会话隔离、结构化来源元数据、
  过期策略及可选向量召回。

## 不立即实施的通用建议

- Markdown 知识库没有天然页码；只有接入 PDF 时才引入 `page` 元数据。
- 当前约 200 个 Chunk 的规模下，BM25 每次由持久化 token 索引重建的成本可接受；规模增长后再考虑
  常驻索引或专用搜索服务。
- Evidence Review 与 Report Verification 当前应保持分离：前者判断证据覆盖，后者判断报告是否忠于证据；
  不为减少一次模型调用而牺牲职责边界。
