# AI Agent 应用开发能力体系

> 目标岗位：国内企业的 AI 应用开发、Agent 应用开发、LLM 应用工程师、Agent 后端工程师。
>
> 本文不是面试题库，也不是要求一次性掌握的技术名词清单。它回答三个问题：真正的岗位能力是什么、每项要学到什么程度、如何用项目证明。

## 1. 先确定岗位边界

“Agent 开发”至少包含三类岗位，不能混用同一套要求。

| 岗位类型 | 主要工作 | 核心门槛 | 本文覆盖范围 |
| --- | --- | --- | --- |
| AI / Agent 应用开发 | 将模型、检索、工具和业务流程组成可用产品 | Python 后端、RAG、工具调用、工作流、评测、稳定性 | **本文主线** |
| Agent Infra / 平台研发 | 提供运行时、编排、网关、沙箱、观测和开发平台 | 分布式系统、容器、调度、基础设施、性能与安全 | 作为进阶方向 |
| 模型算法 / 推理优化 | 训练、微调、对齐、推理加速和底层算子 | Transformer、训练方法、CUDA/MLU、推理框架 | 只保留应用岗需要的基础 |

因此，普通 Agent 应用岗不要求同时精通 CUDA、模型训练、A2A、多 Agent、前端、编译器和所有数据库。面经中出现这些内容，可能是岗位特化题，也可能只是题库拼贴。

## 2. 能力等级：到底要学到什么程度

本文对每项能力采用四级标准。

| 等级 | 含义 | 面试中的表现 |
| --- | --- | --- |
| L0 听说过 | 知道名词，无法解释用途和边界 | 只能给定义 |
| L1 能解释 | 能说清原理、适用场景和主要取舍 | 能回答基础追问 |
| L2 能实现 | 能独立完成可运行实现，并处理常见失败 | 能结合代码和项目回答 |
| L3 能验证和治理 | 能通过数据证明改进有效，能排障、降级并控制风险 | 能回答生产环境深挖 |

目标不是所有内容都达到 L3：

- 核心应用能力达到 **L2**，其中 RAG、工具调用、工作流和评测至少有两项达到 **L3**。
- 后端工程、安全和部署达到 **L1～L2**。
- 模型原理、Multi-Agent、MCP、Skills 等外围主题达到 **L1**，用到时再升到 L2。
- 岗位特化内容只按目标 JD 准备。

## 3. 总体能力地图

```text
业务问题与效果指标
        │
        ▼
LLM 基础与结构化输出 ──→ Context / Memory
        │                         │
        ▼                         ▼
工具系统与 Agent Loop ──→ 工作流、状态与协作
        │                         │
        ├──────────┬──────────────┘
        ▼          ▼
       RAG       外部业务系统
        │          │
        └────┬─────┘
             ▼
      评测、Trace、Bad Case
             │
             ▼
可靠性、安全、成本、部署与产品化
```

这张图比框架名称重要。LangGraph、Agents SDK、AutoGen、CrewAI 等只是实现方式，不能替代对数据流、控制流和失败边界的理解。

## 4. 业务理解与项目表达

### 4.1 应掌握内容

- 用户是谁，原流程的问题是什么，为什么需要 LLM 或 Agent。
- 成功标准是什么：准确率、任务成功率、人工节省时间、处理吞吐、延迟、成本或风险降低。
- 为什么不是普通规则、搜索、分类模型或固定工作流。
- 个人负责的模块、关键取舍、失败案例和量化改进。
- 项目边界：哪些能力已经实现，哪些只是设计，哪些不适合自动化。

### 4.2 目标深度：L3

能够用三种长度讲同一个项目：

- 30 秒：问题、方案、结果。
- 2 分钟：完整链路、个人职责、关键取舍。
- 5～10 分钟：失败案例、评测、工程约束和下一步。

不能只说“使用 LangGraph、向量数据库和大模型搭建 Agent”。框架名不构成项目产出。

### 4.3 面试验证方式

- 为什么要做这个项目？
- 最大难点是什么？有哪些方案被放弃？
- 如何证明优化后更好？
- 如果删除 LLM，这个系统还剩什么？
- 如果用户量扩大十倍，最先出现什么问题？

### 4.4 当前项目证据

Autonomous Research Agent 已有清晰的问题定义、证据驱动工作流、项目边界和版本路线图。下一步应补充一页可复现的量化结果摘要，以及一个完整 Bad Case 的修复前后对比。

## 5. Python 与后端工程基础

### 5.1 Python 语言能力

必须达到 L2：

- 数据结构、函数、类、异常、上下文管理器、类型标注。
- 迭代器与生成器，知道惰性计算适合流式和大数据处理。
- 装饰器的用途：日志、计时、重试、权限和缓存；理解闭包和 `functools.wraps`。
- `asyncio`、协程和事件循环；知道异步函数中调用阻塞 I/O 会拖住整个事件循环。
- 多线程适合 I/O 密集，多进程适合 CPU 密集；理解 GIL 的工程影响。
- `Lock`、`RLock`、Semaphore 的基本用途，不要求背操作系统源码。

### 5.2 服务端能力

应用岗目标为 L2：

- HTTP API、JSON Schema、请求校验、错误码、认证与配置管理。
- FastAPI 或同类框架；同步与异步接口的边界。
- SSE 的事件格式、心跳、代理缓冲、断连检测和取消传播。
- WebSocket 与 SSE 的选择：单向增量输出通常 SSE 足够，双向实时交互再考虑 WebSocket。
- 长任务不能长期占用普通请求线程；使用后台任务、队列、任务 ID、进度状态和取消机制。
- 数据库事务、索引、连接池；Redis 的缓存、会话、分布式锁或队列用途。
- 并发修改同一会话时使用版本号、乐观锁、串行队列或幂等键避免覆盖。

### 5.3 可靠性基本功

- 超时必须分层设置：连接、读取、单工具、整次任务。
- 重试只用于可恢复错误，并使用退避、抖动和次数上限。
- 有副作用的操作重试前必须解决幂等问题。
- 熔断用于快速隔离持续失败的下游；降级用于保留核心能力。
- 限流需要同时考虑用户、租户、模型、工具和全局资源。
- 错误返回结构化类型，不把异常文本直接喂给模型自由发挥。

### 5.4 面试合格线

给出“模型调用慢、工具超时、SSE 断开、同一 Session 并发写入”等场景时，能够画出请求链路、找到潜在阻塞点，并提出可验证的修复方法。

### 5.5 当前项目缺口

- 已有：Python 3.11、类型化状态、网络超时、错误归一化、单元测试、运行入口。
- 待补：FastAPI、SSE、后台任务、任务取消、数据库持久化、Redis、接口认证和分布式并发控制。

## 6. LLM 基础、Prompt 与结构化输出

### 6.1 模型基础：应用岗达到 L1

- 输入最终会被 Tokenize，并转换为 token ID 和向量表示。
- Self-Attention 用 Q、K、V 计算当前位置对其他位置的信息聚合；同一 token 的静态词嵌入可以相同，但经过位置编码和上下文层后表示不同。
- Temperature、Top-p、最大输出长度等参数对稳定性、成本和截断的影响。
- 上下文窗口是输入与输出共享的有限预算；“支持长上下文”不代表模型能同等利用每个位置的信息。
- SFT、LoRA、DPO/RLHF 是模型层优化路径；应用问题优先检查数据、Prompt、检索、工具和工作流。

不要求应用岗现场完整推导 Attention 公式，除非 JD 明确偏算法。

### 6.2 Prompt 与 Context Engineering：达到 L2

- 明确角色、目标、输入边界、约束、成功标准、拒答条件和输出 Schema。
- Few-shot 用于展示分类边界、格式和难例；示例必须覆盖真实错误模式。
- 不依赖让模型暴露隐藏思维链；用可观察的计划、结构化中间结果和工具结果表达过程。
- 将稳定规则放在系统或开发者指令，将运行时数据放在输入、检索或工具中。
- 区分模型上下文和应用本地状态：数据库连接、用户身份、日志器等不应无意义地进入 Prompt。
- 对长任务维护目标、约束、已完成事项、待办和证据索引，而非不断追加完整历史。

### 6.3 结构化输出：达到 L2～L3

- 使用 JSON Schema / Pydantic 等定义输出契约，枚举和必填字段尽量收紧。
- 校验模型输出；失败时可进行一次受控修复，不能无限“请重新输出 JSON”。
- 处理最大 Token 导致的 JSON 截断，区分语法错误、字段缺失和业务不合法。
- 下游不能把模型生成的 SQL、URL、文件路径或命令当作可信输入。
- 结构化输出保证格式，不保证事实正确；内容仍需业务校验或证据验证。

### 6.4 Query Rewrite

- 只在代词、省略、表达噪声、多轮指代或检索词不充分时启用，不是每个请求都重写。
- 原始 Query 必须保留；重写结果应是检索辅助，不应悄悄改变用户目标。
- 可并行检索原 Query 与改写 Query，再融合结果。
- 低置信度或关键槽位缺失时，向用户澄清比猜测更可靠。
- 用固定评测集验证重写是否提高召回，而不是默认“多一步 LLM 一定更好”。

### 6.5 当前项目证据

项目已使用结构化证据评估和报告验证、明确区分本地运行状态与正式 Evidence，并在缺少关键信息时进入澄清分支。Query Rewrite 尚未作为独立可评测模块实现。

## 7. 工具系统、Function Calling、MCP、Skills 与 Harness

### 7.1 概念边界

| 概念 | 解决的问题 | 不等于什么 |
| --- | --- | --- |
| Function Calling / Tool Calling | 让模型按 Schema 提议调用应用提供的函数 | 不负责函数本身的安全和成功 |
| MCP | 用统一协议暴露工具、资源和提示，使客户端可发现和连接能力 | 不是新的推理算法 |
| Skill | 可按需加载的专业流程包，包含说明、模板、脚本或参考资料 | 不只是一个长 Prompt |
| Harness | 承载 Agent 的运行外壳：上下文、工具、循环、权限、状态、观测和恢复 | 不等于底层模型 |

普通应用开发岗位：Function Calling 达到 L2～L3；MCP、Skills、Harness 达到 L1，项目需要时再实现。

### 7.2 工具设计：达到 L3

一个生产可用工具需要：

- 单一、清晰的职责；名称和描述说明何时用、何时不用。
- 严格参数 Schema、枚举、范围、长度和格式校验。
- 结构化返回：状态、数据、错误类别、是否可重试、来源或版本。
- 稳定语义；工具描述与实际行为一致。
- 超时、重试、幂等、限流、权限和审计。
- 读操作与写操作分离；高风险副作用需要人工审批。
- 返回结果需要清洗、长度限制和不可信内容隔离。

### 7.3 Agent Loop

最小循环为：理解目标 → 选择行动 → 调用工具 → 观察结果 → 更新状态 → 判断继续或结束。

必须存在确定性控制：

- 最大模型轮次、最大工具调用数、总时间和 Token/成本预算。
- 对“同一工具 + 等价参数 + 无状态进展”的重复调用做循环检测。
- 完成条件不能只相信模型自报；关键任务需要结果校验器。
- 工具不可用时区分重试、替代工具、降级答案、人工接管和终止。
- 任何重试都必须消耗预算，防止另一种形式的死循环。

### 7.4 错误处理决策

| 错误 | 常见处理 |
| --- | --- |
| 参数不符合 Schema | 本地拒绝；允许模型基于明确错误修正一次 |
| 临时网络错误、限流 | 有界退避重试，必要时切换备用服务 |
| 权限不足 | 不重试；返回明确边界或请求授权 |
| 工具不存在或模型选错 | 路由纠正、候选工具收缩或停止 |
| 返回脏数据 | Schema 校验、字段清洗；不合格结果不得成为证据 |
| 有副作用操作结果不确定 | 查询操作状态或使用幂等键，禁止盲目重放 |
| 依赖长期不可用 | 熔断并降级到较弱但可用的路径 |

### 7.5 当前项目证据

- 已有：四个真实工具、Pydantic/Tool Schema、未知工具错误、工具失败不进入 Evidence、工具预算、重复证据去重、外部搜索与正文读取分离、网络超时。
- 待补：通用重试策略、幂等键、熔断器、工具权限分级、动态工具选择、人工审批和更强沙箱。

## 8. RAG 与知识工程

### 8.1 完整链路：达到 L3

```text
数据源识别
  → 解析与清洗
  → 结构化分块与元数据
  → Embedding / 词法索引
  → Query 理解与过滤
  → 多路召回
  → 融合、去重、按文档聚合
  → Rerank
  → Context 选择与排序
  → 带证据生成
  → 检索和生成分开评测
```

### 8.2 数据清洗与分块

- 清除导航、页眉页脚、重复模板、乱码和无意义书目列表。
- 保留标题层级、来源、时间、文档 ID、权限、版本和业务标签。
- 优先按语义和结构边界切分；固定 Token 长度是兜底，不是唯一策略。
- Chunk 应保持最小可回答单元，同时保留父文档和邻接关系。
- overlap 用于缓解边界信息断裂，但会增加重复召回、存储和上下文成本。
- 表格、代码、图片和扫描 PDF 需要专门解析；不能强行当普通段落。
- 多版本文档需要生效时间、版本过滤或去旧策略。

Chunk Size 和 overlap 没有通用最优值，应通过真实问题集比较召回与最终答案效果。

### 8.3 召回、融合与重排

- BM25 对专有名词、编号、版本号、错误码和精确短语强。
- Dense Retrieval 对同义表达和语义相近问题强，但可能漏掉精确实体。
- 混合检索用于提高候选覆盖；不能直接相加不同量纲的原始分数。
- RRF 按排名融合，适合缺少可靠分数校准时作为稳健基线。
- Reranker 联合判断 Query 与候选片段的相关性，通常放在较小候选集上，避免延迟和成本失控。
- 召回结果以 chunk 为单位，但用户通常需要文档级答案；应去重、聚合并控制单一文档占比。
- Top-K 的选择需要综合 Recall、上下文预算、Rerank 能力和延迟，通过评测确定。

### 8.4 长文档和亿级检索

- 离线解析、分块、Embedding 与增量更新；在线请求不重复做重活。
- 使用 ANN 索引、分片、元数据预过滤、缓存和批量请求。
- 候选召回与精排分层，避免对全库运行 Cross-Encoder。
- 索引版本、文档版本与删除传播必须可追踪。
- 容量规划关注向量维度、数据规模、QPS、P95/P99、更新频率和过滤条件。

### 8.5 RAG 失败诊断

| 症状 | 优先检查 |
| --- | --- |
| 正确资料没有进入候选 | 解析、分块、索引、过滤、Embedding、Query 表达、候选 K |
| 候选中有正确资料但排名低 | 融合方法、Rerank、元数据权重、重复 chunk |
| Context 有正确证据但答错 | Prompt、上下文排序、冲突来源、模型能力、问题拆解 |
| 回答正确但引用错误 | Evidence ID、引用绑定、生成后验证 |
| 文档过期导致错误 | 版本、有效期、增量更新和删除机制 |
| 多跳问题丢信息 | 子问题状态、证据集合、依赖图和最终综合 |

### 8.6 评测指标

检索层与生成层必须分开：

- 检索：Recall@K、Precision@K、MRR、NDCG、命中正确来源比例。
- Rerank：正确候选排名变化、NDCG/MRR、延迟和失败率。
- 生成：答案正确性、忠实度、证据覆盖、引用正确率、拒答质量。
- 端到端：任务成功率、人工通过率、延迟、成本和 Bad Case 类型分布。

LLM-as-Judge 只是一种近似评测器，要通过顺序交换、匿名化、长度控制、多评委或人工抽检降低位置、风格和长度偏差。

### 8.7 当前项目证据

项目已实现 Markdown 清洗与分块、Chroma 向量召回、中文 BM25、RRF、Qwen Rerank、受控回退、可追踪来源，以及纯向量 / RRF / RRF+Rerank 的固定问题集评测。这是当前最接近 L3 的能力模块。

后续重点：扩大人工标注集、增加版本/权限元数据、加入引用正确性和答案忠实度指标，并记录真实性能数据。

## 9. 工作流、状态、Checkpoint 与 Human-in-the-loop

### 9.1 Workflow 还是 Agent

- 路径明确、规则稳定、合规要求高：优先固定 Workflow / DAG。
- 步骤数量难以预先确定、需要基于环境反馈动态决策：考虑 Agent Loop。
- 很多系统是混合形态：确定性外层工作流包住少量 Agent 节点。
- 复杂度必须由评测证明价值；能用一次调用或固定链解决，就不增加 Agent 自主性。

### 9.2 状态设计：达到 L2～L3

状态至少区分：

- 用户目标和不可违反的约束。
- 会话消息与精简后的模型上下文。
- 计划、当前步骤、待办和完成进度。
- 工具调用及其结构化结果。
- Evidence、候选资料与正式证据。
- 错误、重试次数、预算和停止原因。
- 最终产物和评测结果。

状态字段是节点之间的公共契约，不应让每个节点自由写入任意字典。并行节点需要明确合并规则，避免最后写入者覆盖其他结果。

### 9.3 Checkpoint 与恢复

- 每个关键节点后持久化可序列化状态，并关联 run/thread ID 和图版本。
- 恢复时从最近安全节点继续，而不是重放全部有副作用操作。
- 图结构或 State Schema 变化时，需要版本号、迁移函数或旧任务冻结策略。
- 保存状态不等于保存所有 Prompt；敏感信息、临时对象和数据库连接不得直接序列化。

### 9.4 Human-in-the-loop

适合暂停的位置：

- 用户意图或关键参数不明确。
- 写入、删除、付款、发送消息等高风险操作之前。
- 证据冲突、低置信度或结论影响较大。
- 计划成本超过阈值或需要扩大权限。

人工长时间不响应时，应保存可恢复状态，并按业务规则超时取消、降级或转人工队列，不能无限占用运行资源。

### 9.5 当前项目证据

项目已有明确 `ResearchState`、有界循环、澄清分支、证据评估、报告验证与修订状态。尚未实现数据库 Checkpoint、跨进程恢复、图版本迁移和真正的人工中断/继续。

## 10. Context 与 Memory

### 10.1 四类信息不要混在一起

| 类型 | 作用 | 常见存储 |
| --- | --- | --- |
| 当前工作上下文 | 完成本次步骤所需的最小信息 | Prompt / 当前 State |
| 会话记忆 | 当前对话的目标、决定、摘要和近期消息 | 会话库、Checkpoint |
| 用户长期记忆 | 稳定偏好、授权资料和历史事实 | 用户隔离的长期存储 |
| 业务知识 | 可引用的组织或领域事实 | RAG、数据库、知识图谱 |

Memory 不是 Evidence。历史摘要可以帮助制定计划，但不能替代本次任务所需的正式来源。

### 10.2 Context Engineering：达到 L2～L3

- 先定义每次模型调用真正需要什么，再构造上下文。
- 保留系统约束、用户目标、最新状态和高价值证据；裁剪低价值闲聊和重复工具输出。
- 对旧对话做结构化摘要，保留决定、未决项、关键实体和来源指针。
- 使用文件路径、文档 ID、URL、查询 ID 等轻量引用，按需加载原文，而非一次性灌入所有资料。
- 重要证据不应全部放在超长上下文中间；上下文长度、位置与答案质量应进入评测。
- 为每类内容设置 Token 预算：规则、历史、证据、工具结果和输出预留。

### 10.3 Memory 写入和召回

- 只写入稳定且未来有用的信息；每条记忆带来源、时间、作用域和置信度。
- 用户、租户、项目之间严格隔离。
- 支持过期、更正、删除和冲突处理。
- 召回策略综合相关性、时间、重要度和权限。
- 防止把模型幻觉或未经验证的工具结果写成长期事实。

### 10.4 当前项目证据

项目已实现本地 Task Memory，只保存通过核验的报告摘要，并明确不把它当作当前 Evidence。尚缺数据库、用户/租户隔离、过期与删除、长期记忆评测和会话压缩策略。

## 11. 单 Agent、Multi-Agent 与协作契约

### 11.1 默认从单 Agent 开始

增加多个 Agent 的合理原因：

- 专家需要完全不同的工具、权限、模型或指令。
- 子任务可并行且收益显著。
- 需要独立校验以降低同一上下文中的确认偏差。
- 单 Agent 的工具和上下文已经复杂到难以稳定路由。

不能仅因为任务看起来复杂就拆成多个 Agent。一个 Agent + 多个 Skill 或确定性子流程通常更便宜、更容易调试。

### 11.2 常见协作模式

- Router：按请求类别选择专家。
- Supervisor：中央协调者动态分配任务并汇总。
- Pipeline：按固定顺序传递结构化结果。
- Parallel workers：拆分独立子任务并发执行。
- Evaluator–optimizer：生成者与校验者循环改进。

### 11.3 结构化交接

Agent 之间不应默认传递完整历史，而应传递最小必要契约，例如：

```json
{
  "task_id": "...",
  "objective": "...",
  "constraints": ["..."],
  "inputs": [{"ref": "...", "purpose": "..."}],
  "result": {"status": "...", "data": {}},
  "evidence_ids": ["..."],
  "confidence": 0.0,
  "open_questions": ["..."],
  "error": null
}
```

完整 Trace 保存给观测系统，而不是全部塞给下游模型。

### 11.4 Multi-Agent 的额外问题

- 延迟、Token 和调用次数增加。
- 路由错误、重复工作、状态冲突和循环委派。
- 上游幻觉被下游当作事实放大。
- 责任难以定位，评测粒度更复杂。
- 不同 Agent 权限组合扩大安全攻击面。

只有 A/B 评测证明质量、速度或隔离收益时，才保留多 Agent 架构。

### 11.5 当前项目状态

当前单 Agent 图已具备明确节点职责，V3 计划的 Coordinator、Research、Event/Data、Verifier 有合理业务边界。但在历史事件数据工具、Checkpoint 和交接评测成熟前，不应为了简历名词提前拆分。

## 12. 评测、Trace 与 Bad Case 闭环

### 12.1 评测优先级：达到 L3

```text
定义业务成功
  → 收集真实样本与失败样本
  → 标注期望结果/证据/行为
  → 分层指标
  → 建立基线
  → 单变量改动
  → 离线回归
  → 小流量上线
  → 线上反馈进入数据集
```

### 12.2 指标分层

| 层级 | 典型指标 |
| --- | --- |
| 业务层 | 任务完成率、人工节省时间、转人工率、错误损失 |
| 最终答案 | 正确性、完整性、忠实度、引用正确率、拒答质量 |
| 行为轨迹 | 工具选择正确率、参数正确率、路由/交接正确率、循环率 |
| RAG | Recall@K、MRR/NDCG、证据覆盖、Rerank 改善 |
| 系统 | P50/P95/P99、错误率、吞吐、可恢复率、可用性 |
| 成本 | 输入/输出 Token、模型成本、工具成本、单成功任务成本 |
| 安全 | 越权率、危险操作拦截率、误拦截率、注入攻击成功率 |

平均分会掩盖严重错误，必须按任务类别、难度、数据版本和用户类型切片。

### 12.3 Trace 应记录什么

- run、用户/租户、模型和配置版本。
- 每个节点开始/结束、耗时、状态变化和停止原因。
- 模型调用的输入摘要、输出类型、Token、延迟和错误。
- 工具名、参数摘要、结果状态、重试和副作用 ID。
- 检索候选、排名阶段、最终 Evidence 和引用关系。
- Guardrail、人工审批和降级决策。

敏感数据需要脱敏和访问控制，Trace 不是无条件保存完整 Prompt。

### 12.4 Bad Case 分类

- 意图或参数理解错误。
- 检索未召回、排序错误、资料过期。
- 工具选择或参数错误。
- 工具失败或返回脏数据。
- 状态丢失、循环、过早结束。
- 有证据但生成错误，或引用不支持主张。
- 安全、权限或隐私问题。
- 延迟、成本或并发问题。

每个 Bad Case 至少记录：输入、期望、实际、失败节点、根因、修复、回归测试和上线结果。

### 12.5 LLM-as-Judge 的边界

- 先定义清晰 Rubric，再使用结构化评分。
- 随机化答案顺序、隐藏模型名，避免位置和品牌偏见。
- 控制答案长度，或把简洁性单独评分。
- 对高风险样本进行人工复核，并校准 Judge 与人的一致率。
- Judge 不应评估自己看不到的事实；事实性任务必须提供参考证据或标准答案。
- 规则、程序断言和人工评测能解决的问题，不必全部交给另一个 LLM。

### 12.6 当前项目证据

项目已有运行级 Trace、节点耗时、检索评测、报告验证评测、结构化 Reviewer 与引用完整性程序检查。下一步应增加业务端到端集、工具选择评测、成本统计、失败切片和稳定的结果基线表。

## 13. 安全、权限与 Guardrail

### 13.1 威胁模型：达到 L2

- 直接 Prompt Injection：用户试图改变系统目标或绕过限制。
- 间接 Prompt Injection：网页、文档、邮件或工具结果中含恶意指令。
- 敏感信息泄露：跨用户数据、凭据、内部 Prompt 或业务秘密进入输出。
- 工具滥用与过度自主：模型拥有不必要功能、权限或无需审批的高风险操作。
- 不安全输出处理：模型输出被直接用于 SQL、Shell、HTML、路径或 API。
- 资源滥用：无限循环、超大输入、并发轰炸和成本耗尽。

Prompt 不是安全边界。RAG 和微调也不能根除 Prompt Injection。

### 13.2 分层控制

- 输入层：身份、租户、长度、格式、内容策略和速率限制。
- 上下文层：外部内容标记为不可信数据，避免与系统指令混合。
- 模型层：最小工具集合、明确拒绝条件和结构化输出。
- 工具层：参数校验、最小权限、资源白名单、超时、审计和沙箱。
- 审批层：写入、删除、支付、发送、生产变更等操作人工确认。
- 输出层：事实/引用验证、敏感信息检测、编码转义和业务规则检查。
- 基础设施层：密钥管理、网络隔离、文件系统边界和租户隔离。

Guardrail 需要靠近风险发生的位置。只检查最终答案，挡不住已经执行的危险工具调用。

### 13.3 当前项目证据

项目已有基础 URL 安全过滤、工具结果准入 Evidence 的边界和有界循环。仍需补充完整 SSRF 防护、Prompt Injection 测试、工具权限模型、秘密管理、租户隔离、输出内容策略和人工审批。

## 14. 性能、成本与生产化

### 14.1 延迟拆解

总延迟通常来自：排队 + 模型首 Token + 模型生成 + 检索 + Rerank + 外部工具 + 重试 + 串行工作流。

优化顺序：

1. 先用 Trace 定位最大耗时段。
2. 删除无价值调用和重复上下文。
3. 独立工具并发；有依赖的步骤不能盲目并发。
4. 简单分类、抽取和路由使用更小模型或确定性代码。
5. 缓存稳定且可安全复用的结果，并设计版本和失效机制。
6. 对慢工具设置超时、备用路径和异步后台模式。
7. 流式输出改善感知延迟，但不减少总计算时间。

### 14.2 成本控制

- Context 裁剪、摘要和按需检索。
- 模型分级路由；高价模型只处理困难步骤。
- Embedding、检索和确定性工具结果缓存。
- 最大轮次、工具数、Token 和总金额预算。
- 对重复或相似请求做安全缓存；用户私有内容必须隔离。
- 监控单请求成本之外，还要看“单成功任务成本”。

### 14.3 部署与运维

- 配置与密钥不进入代码仓库。
- 容器化、健康检查、滚动发布和快速回滚。
- 无状态 API 与外部状态存储，支持横向扩容。
- 模型、Prompt、图、工具和 Schema 都需要版本标识。
- 依赖下游设置连接池、隔离舱、超时和容量上限。
- SLO、告警、日志、Trace、指标和成本仪表盘。
- 对长任务支持查询、取消、恢复和过期清理。

### 14.4 当前项目缺口

项目目前是本地 CLI 学习系统，尚未实现 API 服务、Docker、持久化任务、认证、限流、监控平台、成本仪表盘和生产发布流程。这些是核心 Agent 能力稳定后的产品化阶段，不应假装已经完成。

## 15. 数据库、缓存与向量索引的必要基础

### 15.1 MySQL / PostgreSQL：达到 L1～L2

- B+ 树索引适合磁盘页和范围查询；联合索引遵循最左前缀的可利用范围。
- 优化器会根据选择性和成本选择索引，不保证多个单列索引一定按想象组合。
- 覆盖索引、回表、事务隔离、MVCC、锁和慢查询基础。
- 会话、任务、Checkpoint、审批和审计数据应使用明确 Schema，而非全部塞进向量库。

### 15.2 Redis：达到 L1～L2

- 用途：缓存、会话、限流、短期状态、任务进度、分布式协调。
- 缓存穿透：空值缓存、布隆过滤器或请求校验。
- 缓存击穿：互斥更新、逻辑过期或 singleflight。
- 缓存雪崩：TTL 抖动、分批预热、限流和降级。
- RDB 与 AOF 的持久化取舍；Redis 不能替代所有持久数据库。

### 15.3 向量索引：应用岗达到 L1

- HNSW：召回好、查询快、内存占用较高，适合中等规模和在线检索。
- IVF：训练后分桶，查询只扫描部分簇，适合更大规模并可调速度/召回。
- 选型要结合规模、更新模式、过滤、内存、延迟和目标 Recall，而不是只背定义。

## 20. 判断自己是否达到可面试标准

当下面问题多数可以用自己的项目、代码、Trace 和数据回答，而不是背概念时，就已经达到真实的应用开发面试线：

- 为什么这里用 Workflow，哪里允许模型自主决策？
- 一个请求从进入系统到最终报告经历哪些节点和状态变化？
- 工具参数错误、超时、重复调用和脏结果分别如何处理？
- 如何证明 BM25 + Dense + Rerank 比纯向量更好？
- 正确资料已经召回但最终回答错误，如何定位？
- 为什么历史 Memory 不能直接当 Evidence？
- 如何避免 Agent 死循环和假装完成？
- SSE 断开后，如何停止或恢复后台任务？
- 如何构造评测集，如何避免 LLM-as-Judge 偏差？
- 哪些操作需要人工审批，为什么 Prompt 不是安全边界？
- 如何统计一次成功任务的延迟和成本？
- 如果换一个底层模型，哪些层应该保持不变，哪些需要回归测试？

## 21. 面经使用规则

以后每遇到一道面试题，只做四步：

1. 归入本文某个能力模块。
2. 判断它是统一核心能力、通用开发基础，还是岗位特化内容。
3. 判断目标深度是 L1、L2 还是 L3。
4. 若项目没有证据，再决定学习或实现；否则只补回答表达。

无法归类、与目标 JD 无关、也不能改善项目的题目，不进入主学习路线。
